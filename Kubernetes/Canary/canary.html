The idea

Run the new version (canary) next to the old one (stable) behind the same Service. Because the Service picks Pods by one shared label, the traffic share follows the share of Pods: 4 stable + 1 canary = 20% canary. Change the replica counts to change the share.

Canary deployment

Release the new version to a small share of users first. If it is healthy, increase the share. If not, remove it.

Stable

The current, trusted version. Most users stay on it.

Canary

The new version, given to a small share of users first.

Replica

One running copy (Pod) of an app.

Label

A key=value tag on an object, like track=canary.

Selector

A filter that picks objects by label. The Service uses it.

Traffic split

The share of requests each version gets. Here: the share of Pods.

Promote / Rollback

Promote = canary for everyone. Rollback = remove the canary.

Create a cluster, a namespace and move into it

~3 min

Goal: Get a clean place to work.

Terminal
# Create a local Kubernetes cluster (skip if you already have one)
kind create cluster --name lab
# Check the cluster is ready
kubectl get nodes
# Create a namespace for the demo
kubectl create namespace canary
# Make it the default namespace for this terminal
kubectl config set-context --current --namespace=canary
Real output from our test run
NAME                STATUS   ROLES           AGE     VERSION
lab-control-plane   Ready    control-plane   2m49s   v1.31.9
namespace/canary created
Context "kind-lab" modified.
What just happened
  • A namespace is a folder inside the cluster. Everything we create lives in canary, so cleanup is one command.
  • set-context --current --namespace=canary makes it the default, so you never type -n canary.
Checkpoint
The node is Ready and the namespace exists.
2

Create all three files with ONE paste

~2 min

Goal: Instead of creating YAML files one by one, copy this single block and paste it once.

Terminal — creates shop-stable.yaml, shop-canary.yaml and service.yaml
# Create the stable (version 1) Deployment file
cat > shop-stable.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-stable
spec:
  replicas: 4
  selector:
    matchLabels: {app: shop, track: stable}
  template:
    metadata:
      labels: {app: shop, track: stable}
    spec:
      containers:
      - name: web
        image: nginx:1.28-alpine
        readinessProbe:
          httpGet: {path: /, port: 80}
        volumeMounts:
        - {name: page, mountPath: /usr/share/nginx/html}
      volumes:
      - name: page
        configMap: {name: page-stable}
EOF
# Create the canary (version 2) Deployment file
cat > shop-canary.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-canary
spec:
  replicas: 1
  selector:
    matchLabels: {app: shop, track: canary}
  template:
    metadata:
      labels: {app: shop, track: canary}
    spec:
      containers:
      - name: web
        image: nginx:1.28-alpine
        readinessProbe:
          httpGet: {path: /, port: 80}
        volumeMounts:
        - {name: page, mountPath: /usr/share/nginx/html}
      volumes:
      - name: page
        configMap: {name: page-canary}
EOF
# Create the Service file (it selects ONLY app=shop, so it matches both versions)
cat > service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  selector: {app: shop}
  ports:
  - {port: 80, targetPort: 80}
EOF
# List the files
ls
Real output from our test run
service.yaml
shop-canary.yaml
shop-stable.yaml
What just happened
  • Each cat > file <<'EOF' writes everything up to the next EOF line into that file.
  • shop-stable.yaml: 4 Pods, labels app=shop and track=stable.
  • shop-canary.yaml: the same, but 1 Pod and track=canary.
  • service.yaml: selects only app=shop, so it matches Pods of BOTH versions. That is the whole canary trick.
Checkpoint
ls shows three files.

Start the stable version (version 1)

~3 min

Goal: Run 4 Pods of the stable version.

Terminal
# Create the stable page (version 1)
kubectl create configmap page-stable --from-literal=index.html='<h1>Shop v1 - STABLE</h1>'
# Look at the stable Deployment file
cat shop-stable.yaml
# Create the stable Deployment (4 Pods)
kubectl apply -f shop-stable.yaml
# Wait until all 4 Pods are ready
kubectl rollout status deployment/shop-stable
# List the Pods with their track label
kubectl get pods -L track

Add the Service and measure

~4 min

Goal: Create the entry point for users and count who answers.

Terminal
# Look at the Service file (it selects only app=shop)
cat service.yaml
# Create the Service
kubectl apply -f service.yaml
# See which Pod addresses the Service found
kubectl get endpoints shop
# Start a small helper Pod for testing
kubectl run tester --image=busybox:1.37 --command -- sleep 3600
# Wait until the helper is ready
kubectl wait --for=condition=Ready pod/tester --timeout=60s
Real output from our test run
service/shop created
NAME   ENDPOINTS                                                  AGE
shop   10.244.0.17:80,10.244.0.18:80,10.244.0.19:80 + 1 more...   0s
pod/tester created
pod/tester condition met
Terminal
# Send 100 requests and count the answers by version
for i in $(seq 1 100); do kubectl exec tester -- wget -qO- http://shop; echo; done | sort | uniq -c
Real output from our test run
    100 <h1>Shop v1 - STABLE</h1>
The measuring command sends 100 requests from the helper Pod, then sort | uniq -c counts how many times each answer appeared. We reuse it after every change.
What just happened
  • The Service selector has only app: shop, so it finds all 4 stable Pods. kubectl shortens the endpoint list (+ 1 more), that is 4 addresses.
  • All 100 answers are version 1: today everyone is on stable.
Checkpoint
100 of 100 answers are Shop v1 - STABLE.

Add the canary: about 20% of users

~4 min

Goal: Start 1 canary Pod next to 4 stable Pods and watch the split.

Terminal

kubectl create configmap page-canary --from-literal=index.html='<h1>Shop v2 - CANARY</h1>'
# Compare the stable and canary files
diff shop-stable.yaml shop-canary.yaml
# Create the canary Deployment (1 Pod)
kubectl apply -f shop-canary.yaml
# Wait until the canary is ready
kubectl rollout status deployment/shop-canary
# List the Pods: 4 stable + 1 canary
kubectl get pods -L track
# The Service found the canary Pod too
kubectl get endpoints shop

6

Increase the canary to about 40%

~3 min

Goal: The canary looks healthy, so give it a bigger share.

Terminal
# Increase the canary to 2 Pods
kubectl scale deployment shop-canary --replicas=2
# Reduce stable to 3 Pods so the total stays 5
kubectl scale deployment shop-stable --replicas=3
# Wait for the new canary Pod
kubectl rollout status deployment/shop-canary
# Measure: about 40% should be canary
for i in $(seq 1 100); do kubectl exec tester -- wget -qO- http://shop; echo; done | sort | uniq -c
Real output from our test run
deployment.apps/shop-canary scaled
deployment.apps/shop-stable scaled
deployment "shop-canary" successfully rolled out
     62 <h1>Shop v1 - STABLE</h1>
     38 <h1>Shop v2 - CANARY</h1>
What just happened
  • In real life you check your dashboards (errors, speed) before each increase.
  • 2 canary + 3 stable = 5 Pods, so the canary gets about 40%.
Checkpoint
About 2 in 5 answers are from the canary.
7

Problem found: roll back in seconds

~2 min

Goal: Remove the canary. Users go back to stable.

Terminal
# ROLLBACK: scale the canary to 0
kubectl scale deployment shop-canary --replicas=0
# Measure: back to 100% stable
for i in $(seq 1 100); do kubectl exec tester -- wget -qO- http://shop; echo; done | sort | uniq -c
Real output from our test run
deployment.apps/shop-canary scaled
    100 <h1>Shop v1 - STABLE</h1>
What just happened
  • Rollback is just scale the canary to 0. No redeploy.
  • Only about 40% of users ever saw the bad version. That small blast radius is the point of a canary.
Checkpoint
100 of 100 answers are Shop v1 - STABLE again.
8

Fixed: promote the canary to 100%

~3 min

Goal: Give everyone the new version, then check the final state.

Terminal
# PROMOTE: scale the canary to 5 Pods
kubectl scale deployment shop-canary --replicas=5
# Scale the old stable version to 0
kubectl scale deployment shop-stable --replicas=0
# Wait until all 5 canary Pods are ready
kubectl rollout status deployment/shop-canary
# Measure: 100% canary
for i in $(seq 1 100); do kubectl exec tester -- wget -qO- http://shop; echo; done | sort | uniq -c
# Look at the final state
kubectl get pods -L track

9

Clean up

~1 min

Goal: Delete everything we created.

Terminal
# Delete everything in the namespace
kubectl delete namespace canary
# Put the default namespace back
kubectl config set-context --current --namespace=default
Real output from our test run
namespace "canary" deleted
Context "kind-lab" modified.
What just happened
  • Deleting a namespace deletes everything inside it. It can take 30 to 40 seconds.
  • Optional: kind delete cluster --name lab removes the whole cluster.
Checkpoint
kubectl get all in the canary namespace is gone.

Troubleshooting

The split is not exactly 80/20
Requests are spread randomly. Send more requests (change 100 to 500) and it gets closer. For an exact percentage you need an Ingress with canary weights or a service mesh.
Pods are ImagePullBackOff on a restricted network
Pre-load the images: docker pull nginx:1.28-alpine busybox:1.37 then kind load docker-image nginx:1.28-alpine busybox:1.37 --name lab.
Answers are all one version after a scale command
Wait a few seconds for the Service endpoints to update, then measure again (kubectl get endpoints shop).
kubectl exec prints a websocket warning
It is a harmless client message; the loop still works.
