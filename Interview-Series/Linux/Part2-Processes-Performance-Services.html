Q11. The server is slow. Where do you start? ★☆☆☆ Beginner

Say in the interview: I check the load average against the number of CPUs, then look at top and vmstat. High user time means a CPU problem, high wait means a disk problem. Then I use ps to find the process.
Common mistake: Rebooting first. You lose the evidence, and the problem comes back.
CommandWhat it does
uptime ; nprocLoad average vs number of CPUs
top -bn1 | head -12CPU, memory and top tasks, once
vmstat 1 3r = waiting for CPU, b = blocked, wa = I/O wait, si/so = swap
ps aux --sort=-%cpu | headTop CPU users
free -hMemory
mpstat 1 1Per-CPU usage (sysstat)

Follow-up: What are the three load average numbers, and what does a load of four mean?
Answer: They are the average number of tasks that run, or wait to run, over one, five, and fifteen minutes. A load equal to the number of CPUs means fully used. Much higher means tasks are waiting.

Q12. One process uses 100% CPU: find it, tame it, stop it ★★☆☆ Junior

Say in the interview: First find it with ps. Lower the priority with renice. Try kill fifteen, the polite stop. Use kill nine only if it ignores you, because it gives no chance to clean up.
Common mistake: Using kill dash nine first. The program cannot save its data or remove its lock files.
CommandWhat it does
ps -eo pid,ppid,pcpu,etime,cmd --sort=-pcpu | headFind the CPU hog
renice +15 -p PIDLower its priority
kill -STOP PID ; kill -CONT PIDFreeze / continue
kill PIDPolite stop (SIGTERM, 15)
kill -9 PIDHard stop (SIGKILL), last resort
ls -l /proc/PID/exe /proc/PID/cwdWhat program, which folder
strace -p PIDLive system calls

Follow-up: How can you see what a running process is doing, without stopping it?
Answer: Look in slash proc slash the process number. And for a live view of system calls, strace -p, with the process number.

Q13. The app was killed: Out of memory ★★★☆ Mid / Senior

Say in the interview: Out-of-memory kills do not show in the app's log. I check the kernel log with dmesg, and the memory limit of the service or container. Then I fix the leak, or raise the limit.
Common mistake: Only adding more memory. If the program leaks, it will use that memory too.
CommandWhat it does
dmesg | grep -i "killed process"Proof of an OOM kill
ps -eo pid,rss,cmd --sort=-rss | headBiggest memory users
cat /proc/PID/oom_scoreChance to be killed first
echo -500 > /proc/PID/oom_score_adjProtect a process (needs privileges)
systemctl show SVC -p MemoryMaxMemory limit of a service

Follow-up: How do you stop the kernel from killing an important process first?
Answer: Lower its oom score adjust, so it is killed last. Better still: set memory limits per service, so one program cannot take everything.

Q14. nginx will not start under systemd ★★☆☆ Junior

Say in the interview: Systemctl status shows that it failed. Journalctl -u shows why. Often it is a port conflict, a config error, or a permission problem. Then nginx dash t, and ss, find the details.
Common mistake: Restarting again and again, without reading the journal.
CommandWhat it does
systemctl status SVCState and the last log lines
journalctl -u SVC --no-pager | tailThe real error
systemctl cat SVCThe unit file in use
nginx -tTest the nginx config
ss -ltnp | grep :80Who owns the port
nginx -t && systemctl reload nginxSafe config change

Follow-up: You change the nginx config on a live server. How do you apply it safely?
Answer: Test first, then reload. If the test fails, the reload never happens. Reload does not drop connections, unlike a restart.

Q15. Write a systemd service with auto-restart ★★☆☆ Junior

Say in the interview: A unit file with Unit, Service and Install. Restart on failure, a normal user, and enable dash -now. Then I test it by killing the process.
Common mistake: Running the app as root, or starting it by hand in a terminal, without a restart policy.
CommandWhat it does
/etc/systemd/system/NAME.serviceWhere your unit file lives
systemctl daemon-reloadRead new/changed unit files
systemctl enable --now NAMEStart at boot AND start now
systemctl status NAMEIs it running?
journalctl -u NAME -fFollow the logs
systemctl show NAME -p NRestartsHow often did it restart

Follow-up: How do you see how often the service restarted?
Answer: Systemctl show, with N restarts. If it restarts again and again, I look at the journal, and I set limits so it does not loop forever.

Q16. Keep a long job running after SSH disconnects ★☆☆☆ Beginner

Say in the interview: Nohup is the quick fix. Tmux is best when I want to come back and see it. Systemd run is best for a real, managed job with logs.
Common mistake: Starting a long job in a normal terminal, and hoping the connection holds.
CommandWhat it does
nohup CMD > out.log 2>&1 &Survive a hangup
tmux new -d -s NAME 'CMD'Detached session
tmux ls ; tmux attach -t NAMEList / come back
systemd-run --unit=NAME CMDTransient service with logs
jobs ; disownDetach a job from your shell

Follow-up: How do you come back to a tmux session later?
Answer: I log in again, and run tmux attach dash t deploy. For a systemd run job, I use journalctl -u long job dash f to follow its output.

Q17. Zombie, orphan and uninterruptible processes ★★★☆ Mid / Senior

Say in the interview: A zombie is a finished process whose parent did not collect it. I cannot kill it. I find the parent with ps, and fix or restart the parent. An orphan is adopted by process one, and a D state process waits for I O.
Common mistake: Trying to kill dash nine a zombie. It is already dead.
CommandWhat it does
ps -eo pid,ppid,stat,cmd | grep defunctFind zombies (state Z)
ps -o pid,ppid,cmd -p PPIDWho is the parent?
kill PARENTZombies are adopted and removed
ps -eo stat,pid,wchan:20,cmd | awk '$1 ~ /^D/'Processes in D state

Follow-up: A process is in D state and kill -nine does nothing. Why?
Answer: It sleeps inside the kernel, waiting for an I O to finish, for example a broken network share. The signal can only be handled after that. The real fix is to repair the disk or the network, or in the worst case, to reboot.

Q18. High load average, but the CPU is idle ★★★☆ Mid / Senior

Say in the interview: High load with idle CPU means tasks are waiting, usually for disk. I check vmstat for wa and b, iostat for the busy disk, and pidstat and the D state list for the process.
Common mistake: Adding more CPUs. The disk is the bottleneck.
CommandWhat it does
uptime ; vmstat 1 5Load, b and wa columns
iostat -xz 1 3Disk %util and await
ps -eo stat,pid,cmd | awk '$1 ~ /^D/'Blocked processes
pidstat -d 1 3Disk use per process
cat /proc/pressure/ioPercent of time stalled on I/O

Follow-up: What is the pressure file, and why is it useful?
Answer: It is a kernel report, per resource, CPU, memory and I O, of how long tasks were stalled. It is more direct than load average, and good for alerting.

Q19. Too many open files ★★★☆ Mid / Senior

Say in the interview: I check ulimit -n, and slash proc, process number, limits, and I count the open files. For a systemd service, I set Limit N O FILE in an override file and restart it.
Common mistake: Editing limits dot conf for a systemd service. Systemd services do not read it.
CommandWhat it does
ulimit -nLimit of this shell
grep 'open files' /proc/PID/limitsLimit of a running process
ls /proc/PID/fd | wc -lDescriptors in use
lsof -p PID | headWhat they are
systemctl show SVC -p LimitNOFILELimit of a service
/etc/systemd/system/SVC.service.d/limits.conf ([Service] LimitNOFILE=65536)Raise it for a service
cat /proc/sys/fs/file-nrSystem-wide use and maximum

Follow-up: What if the number of open files keeps growing, even after you raise the limit?
Answer: Then the program leaks descriptors. I use lsof, to see what kind of files they are, and I tell the developers. Raising the limit only delays the crash.

Q20. A cron job does not run (or runs twice) ★★☆☆ Junior

Say in the interview: Cron has a tiny environment. Use full paths, send output to a log, and read the cron journal. Use flock -n to stop overlapping runs.
Common mistake: Testing only in your own terminal, with your own PATH.
CommandWhat it does
crontab -l ; crontab -eList / edit jobs
journalctl -u cron | tailDid cron start the job?
CMD >> /tmp/job.log 2>&1Capture the output
use /full/path/to/toolCron has a short PATH
flock -n /tmp/job.lock CMDDo not run twice at once
systemctl list-timerssystemd timers instead of cron

Follow-up: What is the modern alternative to cron on systemd servers?
Answer: Systemd timers. They log to the journal, can run missed jobs after a reboot, and a timer can never overlap its own service by default.
