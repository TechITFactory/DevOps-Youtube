Q1. Your first two minutes on a new server ★☆☆☆ Beginner

Say in the interview: In two minutes I check: who I am, which machine and system this is, the load, the disk, the memory, the network, and the top processes. Look first, change nothing.
Common mistake: Changing things before you understand what the server does.
CommandWhat it does
whoami ; hostnameWho am I? Which machine?
cat /etc/os-releaseWhich Linux, which version
uname -rKernel version
uptimeHow long up, and the load average (1, 5, 15 minutes)
df -hDisk space, human sizes
free -hMemory and swap
ip -br addrNetwork interfaces and IPs, short table
ps aux --sort=-%mem | headBiggest memory users
awk -F: '$3==0 {print $1}' /etc/passwdAccounts with root power (should be only root)

Follow-up: What if you think someone has broken into this server?
Answer: I would also check recent logins, new scheduled jobs, and open ports. And I would tell the security team before I change anything.

Q2. Find the file that changed yesterday ★☆☆☆ Beginner

Say in the interview: I list files by time, use find with mtime, or newer, and then compare the content with a good copy.
Common mistake: Opening every file by hand, instead of letting find narrow it down.
CommandWhat it does
ls -lt DIRNewest files first
find DIR -type f -mtime -1Changed in the last 24 hours
find DIR -type f -newer GOODFILENewer than a known good file
find / -xdev -type f -size +100MBig files, stay on one filesystem
grep -rn "text" DIRSearch inside all files, show line numbers
locate NAMEVery fast search from an index (run updatedb first)

Follow-up: On a very big server, find takes minutes. How do you search the whole disk faster?
Answer: On huge servers, I may also use locate, which searches a ready-made index, so it answers very quickly.

Q3. Permission denied when running a script ★☆☆☆ Beginner

Say in the interview: Two checks. The file needs the x bit, and every folder on the path needs x too. Namei -l shows both.
Common mistake: Using chmod seven seven seven on everything. It removes the error, and it removes your security.
CommandWhat it does
ls -l FILESee the permission bits (rwx)
chmod +x FILEAdd the execute permission
namei -l /full/path/filePermissions of EVERY folder on the path
chmod 755 DIREveryone may enter and read, only owner writes
file script.shShows 'CRLF line terminators' if made on Windows
sed -i 's/\r$//' script.shRemove Windows line endings

Follow-up: The file has execute permission, but you still get an error, even as root: required file not found. What is wrong?
Answer: Other causes: the folder is mounted with noexec, or the program named in the first line does not exist.

Q4. Give a team access to a shared folder ★★☆☆ Junior

Say in the interview: A group plus setgid for the team, and an ACL for one-off exceptions.
Common mistake: Making the folder world-writable with chmod seven seven seven.
CommandWhat it does
groupadd devsCreate a group
usermod -aG devs USERAdd a user to a group (keep other groups)
chgrp -R devs DIRGive a folder (and contents) to a group
chmod g+w DIR ; chmod g+s DIRGroup can write; new files inherit the group (setgid)
setfacl -m u:USER:rwx DIRExtra permission for one named user (ACL)
getfacl DIRShow the ACLs
sg devs -c 'id -gn' / newgrp devsUse a new group without logging out

Follow-up: Bob says he was added to the group, but he still cannot write. Why?
Answer: So I tell Bob to log out and log in again, or to run new group devs. Group changes apply to new sessions.

Q5. Remove a leaving employee, safely ★★☆☆ Junior

Say in the interview: Lock, expire, remove sudo, kill processes, clean cron and keys, back up, and only then delete.
Common mistake: Running user del dash r first. You lose his files, and you may break services that ran as him.
CommandWhat it does
id USERGroups of the user (sudo?)
passwd -l USERLock the password
usermod -e 1 USERExpire the account (SSH keys stop working too)
gpasswd -d USER sudoRemove from the sudo group
pkill -u USERKill all processes of the user
crontab -l -u USER ; crontab -r -u USERShow / remove scheduled jobs
mv ~USER/.ssh/authorized_keys{,.off}Disable SSH keys, keep as evidence
find / -xdev -user USERFiles the user owns
tar czf backup.tgz -C /home USERBack up the home folder
userdel USER ; find / -xdev -nouserDelete last, then check orphan files

Follow-up: After you delete Dave, what file problem can you get?
Answer: So I give such files to someone else with chown, before I delete the user.

Q6. Let a user restart nginx, and nothing else ★★☆☆ Junior

Say in the interview: A rule in sudoers.d, exact commands only, checked with visudo -cf, and tested both ways.
Common mistake: Giving alice ALL, or allowing a program like vim or less. They can open a shell inside it, and become root.
CommandWhat it does
sudo -l -U USERWhat may this user do with sudo?
visudo -cf FILECHECK the syntax before you save
/etc/sudoers.d/NAME (mode 440)Put your rules in their own file
USER ALL=(root) NOPASSWD: /exact/commandThe rule: user, as root, only this command
sudo -n COMMANDTest: do not ask for a password
sudoedit FILESafe way to edit a file as root

Follow-up: The team also wants to edit the nginx config. Can you allow sudo vim?
Answer: So the edit is allowed on one file, and nothing else.

Q7. Top 5 IP addresses in a 2 GB log ★★☆☆ Junior

Say in the interview: Awk picks a column, then sort, uniq -c, sort -nr, and head. This pipeline solves most log questions.
Common mistake: Using unique without sort first. Unique only counts lines that are next to each other.
CommandWhat it does
awk '{print $1}' LOG | sort | uniq -c | sort -nr | head -5Top 5 IPs (column 1)
awk '{print $9}' LOG | sort | uniq -c | sort -nrCount status codes (column 9)
awk '$9==404 {print $7}' LOG | sort | uniq -c | sort -nr | headPages that return 404
zcat LOG.gz | awk ...Read compressed logs without unzipping
wc -l LOGCount lines = requests

Follow-up: The older logs are compressed, in GZ files. Do you unzip them first?
Answer: That is how I check many rotated logs, without filling the disk.

Q8. Deleted a big file, space did not return ★★★☆ Mid / Senior

Say in the interview: Ifdf is much bigger than du, a deleted file is held open. Find it with lsof +L1, then restart the program, or empty the file through slash proc.
Common mistake: Rebooting the whole server for this, or deleting even more files.
CommandWhat it does
df -h ; du -sh DIRCompare: a big gap = a deleted file is still open
lsof +L1List open files that were deleted
ls -l /proc/PID/fd | grep deletedSee the deleted file of a process
cp /proc/PID/fd/N rescue.logRecover the data
: > /proc/PID/fd/NEmpty it to free the space
truncate -s 0 FILEEmpty a log safely instead of rm

Follow-up: How do you avoid this problem next time?
Answer: Better still, use logrotate, which does this safely for you. We will see it in part three.

Q9. SUID, SGID and the sticky bit (audit) ★★★☆ Mid / Senior

Say in the interview: SUID runs a file as its owner. SGID runs it as its group. Sticky protects shared folders. Audit with find perm 4000, and investigate anything unexpected.
Common mistake: Putting S U I D on scripts or editors. It is never needed, and it is very dangerous.
CommandWhat it does
ls -l FILEs in rws = SUID/SGID, t at the end = sticky
find / -xdev -perm -4000 -type fFind all SUID files
find / -xdev -perm -2000 -type fFind all SGID files
chmod u+s FILE / g+s DIR / +t DIRSet SUID / SGID / sticky
mount -o nosuid,noexec,nodev ...Block SUID and programs on a mount

Follow-up: How can you stop SUID programs from working in folders like tmp?
Answer: In real life, these options go into the fstab file, for tmp, var tmp, and dev shm.

Q10. Copy 50 GB safely, resume, and prove it ★★☆☆ Junior

Say in the interview: Rsync with -a, a dry run first, resume by running the same command again, and prove it with a checksum.
Common mistake: Using cp or scp for huge copies. They start again from zero when something breaks.
CommandWhat it does
sha256sum FILE > list.shaFingerprint
sha256sum -c list.shaVerify the fingerprint
rsync -avn SRC/ DST/DRY RUN: show, do nothing
rsync -avP SRC/ DST/Copy with progress; run again to resume
rsync -avz -e ssh SRC/ user@host:DST/Copy to another server over SSH
SRC/ vs SRCSlash = contents. No slash = the folder itself

Follow-up: What is the famous trailing slash trap in rsync?
Answer: So I always do a dry run first, to see where the files will land.
